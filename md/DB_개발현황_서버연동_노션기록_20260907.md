## 3. 현재 데이터 처리 구조

```text
Mode 3/4 시작
  → Jetson mission_id 생성 또는 ACTIVE mission 복구
  → map → base_link 경로 기록
  → route_points 누적

Mode 4에서 YOLO 사람 탐지
  → Jetson이 서버 왕복 없이 즉시 정지
  → 탐지 당시 로봇 pose 강제 기록
  → Jetson detection_id 생성
  → route_end_seq 고정
  → 대표 이미지 저장
  → /mission/detection_event 발행
  → REST outbox 등록

서버 정상 연결 시
  → 지도 ACK
  → mission ACK
  → 탐지 시점까지의 route ACK
  → detection ACK 및 victim 생성
  → 대표 이미지 ACK
  → 같은 detection_id로 VLM 판정과 구호물품 저장
  → GUI에서 경로·빨간 점·상세정보 표시
  → VLM 판단 완료 후 /vlm/injury_stop=0
```

## 6. Jetson DB 테이블

| 테이블 | 주요 내용 |
| --- | --- |
| `schema_meta` | DB schema version |
| `missions` | mission ID, robot/map ID, 시작·종료 시각, mode, status, 종료 원인 |
| `route_points` | route 순번, `map` 기준 `x/y/yaw`, segment, pose jump 품질 정보 |
| `detections` | 탐지 ID, 탐지 시각, 로봇 pose, `route_end_seq`, map, YOLO 정보, 이미지 |
| `outbox` | REST payload·파일, 상태, 시도 횟수, 오류, 다음 재시도, 서버 ACK |

### Outbox 상태

| 상태 | 의미 |
| --- | --- |
| `PENDING` | 아직 보내지 않았거나 전송 대기 |
| `FAILED` | 일시 오류, backoff 뒤 재시도 가능 |
| `BLOCKED` | 인증·schema·ID·파일 등 운영자 조치가 필요한 오류 |
| `SENT` | 서버의 저장 완료 ACK 확인 |

서버 DB 전체를 덮어쓰지 않는다. UUID와 `(mission_id, route_seq)`를 기준으로 필요한
레코드만 추가하며, 서버 ACK를 받은 이벤트만 `SENT`로 전환한다.

